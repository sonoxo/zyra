## Why somebody should come back

```text
MISSION
  ↓
RESULT
  ↓
EVIDENCE
  ↓
KNOWLEDGE
  ↓
PERSONALIZED CONTEXT
  ↓
BETTER NEXT MISSION
```

Long-term user value should accumulate in:

1. **Mission history** — what ZYRA has done with/for the user.
2. **Projects** — repositories, applications and environments.
3. **Agents** — workflows and automations the user has created.
4. **Intelligence** — sources, entities, observations and relationships.
5. **Evidence** — results, provenance, audit and verification.
6. **Recommendations** — what matters next based on real state.

# 9. Update protocol

This bulletin should be updated whenever any of these occur:

- a material feature is added or removed;
- a module changes state (planned → implemented → CI verified → deployed);
- a new ecosystem product/integration is introduced;
- beginner onboarding/navigation changes;
- a significant external collaboration/proposal changes status;
- a policy/authorization boundary changes;
- a major workflow breaks or is restored;
- the priority build order changes.

Each update must answer:

1. **What changed?**
2. **What can a beginner do now that they could not do before?**
3. **What state changed: planned, implemented, CI verified, deployed, externally authorized?**
4. **Does documentation need updating?**
5. **Does US-CZ/policy posture change?**
6. **What is the single highest-value next build?**

Do not convert unverified capability into a stronger status. `Implemented`, `CI verified`, `deployed`, `platform access`, `government authorized` and `partnered` remain separate claims.

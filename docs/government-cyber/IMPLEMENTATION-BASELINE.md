# XUNIA Government Cyber Implementation Baseline

## Baseline objective

This document defines how public government cybersecurity guidance is applied to ZYRA/XUNIA without overstating compliance or importing restricted information.

## 1. Governance and scope

**Primary references:** NIST CSF 2.0, NIST SP 800-53 Rev. 5.

Required implementation artifacts:

- system inventory and system boundary;
- security owner and control owners;
- risk register;
- data-flow diagram;
- control applicability statement;
- evidence index;
- change-management and exception process.

No framework is considered "implemented" merely because its PDF or URL exists in the repository.

## 2. Machine-readable controls

**Primary reference:** NIST OSCAL.

Use OSCAL-compatible concepts for:

- catalogs;
- profiles;
- component definitions;
- system security plans;
- assessment plans;
- assessment results;
- plans of action and milestones.

Where practical, consume official NIST OSCAL content directly from the authoritative NIST repositories instead of manually reproducing control text. Pin the consumed release or commit and record a digest.

## 3. Identity and Zero Trust

**Primary references:** NIST SP 800-207 and NSA Zero Trust Implementation Guidelines.

Minimum XUNIA behavior:

- no implicit trust based solely on network location;
- authenticate the actor or workload;
- authorize each sensitive action;
- least-privilege scopes for agents and tools;
- short-lived credentials where supported;
- privileged access separated from ordinary operation;
- security-relevant access decisions logged;
- policy changes subject to review.

## 4. Secure software development

**Production reference:** NIST SP 800-218 SSDF v1.1.

The SP 800-218 Rev. 1 / SSDF v1.2 initial public draft is tracked for change awareness but MUST NOT replace the final production baseline until NIST publishes it as final.

Minimum controls:

- protected main branch;
- peer or automated review before merge;
- dependency inventory;
- secret scanning;
- vulnerability scanning;
- reproducible/reviewable build process where feasible;
- release provenance;
- documented remediation workflow;
- separation of development and production secrets.

## 5. Technology hardening

**Primary reference:** public DISA STIG/SRG library.

Process:

1. Inventory the actual technology and version.
2. Identify the applicable public STIG/SRG.
3. Record version/release metadata.
4. Translate checks into automated tests only when the source supports it.
5. Test configuration changes in non-production before rollout.
6. Record deviations and rationale.
7. Never treat a STIG mapping as a DISA approval.

Do not fetch CAC-only material.

## 6. Vulnerability management

**Primary references:** CISA KEV, CISA CPGs, NIST SP 800-53.

Prioritization inputs:

- CISA KEV membership;
- external exposure;
- asset criticality;
- exploit maturity;
- privilege required;
- business impact;
- compensating controls.

KEV status raises priority but does not replace environment-specific risk analysis.

## 7. Incident response

**Primary reference:** NIST SP 800-61 Rev. 3.

Required artifacts:

- incident-response plan;
- severity levels;
- contact/ownership model;
- evidence-preservation procedure;
- containment playbooks;
- recovery criteria;
- post-incident lessons learned;
- periodic exercise records.

Agent actions during incidents remain bounded by authorization and must not silently disable security controls or destroy evidence.

## 8. CUI profile

**Primary references:** NIST SP 800-171 Rev. 3 and SP 800-171A Rev. 3.

Default state: **not applicable / disabled**.

Mapping 800-171 into XUNIA does not authorize CUI handling. The CUI profile may only be activated when a real contractual/legal requirement, approved system boundary, appropriate safeguarding environment, and assessment process exist.

## 9. Cyber workforce ontology

**Primary references:** DCWF and DoDM 8140.03.

Represent:

- workforce element;
- work-role ID/title;
- role definition;
- tasks;
- knowledge, skills, and abilities;
- proficiency/qualification concepts;
- training/evaluation mappings.

Do not create a service-member intelligence or personnel database. Individual identities are unnecessary for the ontology.

## 10. AI and LLM governance

**Primary references:** NIST AI RMF 1.0 and NIST AI 600-1.

Every deployed model/agent should have:

- owner;
- intended use;
- prohibited use;
- model/system card;
- input/output data classification;
- tool permission manifest;
- evaluation suite;
- known limitations;
- security tests;
- monitoring;
- incident process;
- version/provenance record;
- human oversight requirements.

Normative government claims generated by an LLM require a source registry reference and should be revalidated if freshness matters.

## 11. DevSecOps architecture reference

**Reference:** DoD Platform One Big Bang public mirror.

Useful concepts include policy enforcement, service mesh, logging, monitoring, runtime security, declarative deployment, and hardened package management. XUNIA can adapt these architectural concepts without claiming it is a Platform One deployment or government-approved environment.

## 12. Evidence standard

A control reaches `verified` only when the repository or operational environment contains evidence adequate to test the mapped requirement. Acceptable evidence may include:

- configuration snapshot;
- automated test result;
- signed review record;
- architecture artifact;
- log excerpt with sensitive data redacted;
- policy file;
- scan output;
- incident exercise record;
- versioned assessment result.

Assertions without evidence remain `planned`, `partially_implemented`, or `implemented_unverified`.

## Implementation order

1. Source/provenance registry.
2. Agent and data safety policy.
3. Control crosswalk.
4. Asset/system inventory.
5. Identity and secrets controls.
6. Logging and vulnerability management.
7. Secure SDLC gates.
8. Technology-specific STIG profiles.
9. Incident response exercises.
10. AI/model evaluations.
11. OSCAL SSP/assessment artifacts.
12. Independent review of claims and evidence.
